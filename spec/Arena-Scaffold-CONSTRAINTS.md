## C1 定位与分层 `[基线：基线§0 / 基线§1 / 基线§19]`

**一句话**：Arena 是建立在 Scaffold 之上的多人结构化讨论系统。

**职责划分**（不可交叉）：

| 层 | 负责 |
|---|---|
| **Arena** | 承载讨论行为：语义确认、论证、质询、投票、分歧展开、用户交互 |
| **Scaffold** | 承载对象与关系：Artifact、Relation、Evidence、Provenance、State、Revision/History |
| **Nested Scaffold** | 承载结构之间的组合关系（默认不启用，见 `§C8`） |

**依赖方向**：Arena `uses` Scaffold；Scaffold `can compose` Nested Scaffold。**不可反向。**

**AI 的定位**：Secretary / Organizer / Detector。**不是 Judge。**

**核心原则**：Arena 不重新发明知识结构。Arena 中产生的东西，一律作为 Scaffold Artifact 管理。

### 非目标

- 不是完整版 Reddit
- 不是完整版「AI 辩论平台」
- 不是通用知识框架

本阶段的唯一目标是 `§T3` 那一条链。范围超出该链的功能，一律不做。

## C2 AI 权限边界 `[基线：基线§0；§C2.0 推论部分、§C2.2–§C2.5 为新增]`

### C2.0 分工（先明确这个，否则下面会被误读）

| 侧 | 负责 |
|---|---|
| **用户** | 用自然语言表达：提问、陈述立场、回应、确认 |
| **AI（机器侧）** | 承担全部**结构化劳动**：语义分割、命题化、分类（Mechanism / Assumption / Counterexample）、质询生成、证据关系提取 |

**推论**：用户不需要学习任何结构化写法。**结构化成本由机器承担**——这是本系统区别于人工论证工具（需作者自行建树）的关键，也是「为什么现在」的答案。

⚠️ **但这个承诺是可被违反的，必须监控。**
若用户必须频繁「换说法」才能被正确切分，成本就**回流到了用户身上**，承诺失效。
判据：**换说法率**（`§C5.6`）。

**权力归属**（基线§11，勿丢）：

> **群众拥有提出和展开议题的权力；系统负责发现相似性、差异性和结构性分歧。**

这条与上面的分工是**一体两面**：

| | 说的是 |
|---|---|
| **分工** | 结构化劳动由**谁**做（机器） |
| **权力** | 议题由**谁**提（用户） |

**系统不得代替用户提出议题**，只能**发现**（相似 / 差异 / 结构性分歧）并**提示**。

### C2.1 允许 `[基线：基线§0]`

- 分割语义（把一段自然语言切成若干命题）
- 整理结构
- 发现相似 / 冲突
- 提示可能的子问题
- 辅助用户补充结构

### C2.2 分割环节的特殊约束 `[新增]`

**在语义分割环节，AI 必须做纯粹分割。**

- 只回答「这句话包含几个命题」，做切分
- **不得**附带建议、倾向、解读、评价
- **不得**暗示哪个命题更成立

（「提示可能的子问题」「发现相似 / 冲突」属于**后续**环节，不得混入分割输出。）

#### C2.2.1 「不得修改」约束的准确含义（极易被误读） `[新增]`

⚠️ **这里要区分四件事，混起来会改错产品形态：**

| | 约束 |
|---|---|
| **原文本本身** | **不可修改**。原文是用户提交的原始材料，必须**原样保存**（`§C2.4`「可追溯」依赖它） |
| **文本的意义** | **不可修改**。分割与规范化不得改变用户想表达的意思 |
| **措辞 / 表述形式** | **可以规范化**。机器为打标签把口语表述规范化，**不违反本约束**——前提是**意义不变** |
| **哪些文本打什么标签、能否进入结构** | **由机器决定，不由用户决定**（见 `§C2.0` 分工） |

**关键**：本约束管的是**意义**，不是**措辞**。

```
原文本   →  不可改（原样保存）
意义     →  不可改
措辞     →  可规范化
标签分配 →  机器决定，不是用户的选择
```

**一处需知情的变化**：母本 `基线§0` 原文是「**偷偷**修改用户表达」，本文件为「修改用户表达」。
「偷偷」是限定词，去掉后约束**收紧**了（从「偷改不行」变成「改不行」）。这是整理时收紧的，不是需求方原意。

#### C2.2.2 用户在这个环节的角色：知情 + 意义校验，不是批准标签 `[新增]`

| 用户**能** | 用户**不能** |
|---|---|
| 指出「这句话的意义被歪曲了」 | 决定「哪段文本被贴上哪个标签」 |
| 看到分割结果与**未采用的部分**（`§C5.2`） | 决定「哪段文本能进入结构」 |

**「给他们看」是必需的，看是权利——但看不是决定权。两者要分开。**

### C2.3 禁止 `[基线：基线§0]`

- 判断哪一方正确
- 给论点打真值分数
- 自动决定观点权重
- 修改用户表达
- 替用户确认语义
- 依据自身判断生成新事实并写入知识结构

### C2.4 每条 AI 产出的结构边都必须可追溯、可推翻 `[新增]`

AI 承担结构化劳动，意味着它产出大量**结构边**：分类判定、`supports / contradicts / qualifies` 关系、质询。

**这些边必须与用户提交的内容同等级别地接受审计。** 对每一条 AI 产出的边：

| 要求 | 含义 |
|---|---|
| **可追溯** | 能指回原文的具体片段 |
| **可拒绝** | 用户能否决任何一条边 |
| **可修改** | 用户能改判定结果 |
| **可计量** | 记录「AI 判定 vs 用户改判」的比例 |

⚠️ **四项都是「能力」，不是「义务」。** 不得要求用户逐条确认这些边——那会造成高频低风险的确认疲劳（见 `§C2.5`）。

正确形态是：

```
默认生效  +  可推翻  +  抽样审计  +  计改判率
```

用户主动推翻时随时可推翻；系统侧靠抽样与改判率做质量监控。

**这是本系统的反向监控指标。** 需分开统计**三个量**：

```
换说法率（§C5.6）           →  结构化成本是否回流到用户   ← 最关键
用户对自己命题的修改率      →  反省是否发生
用户对 AI 结构边的改判率    →  结构化是否可信
```

**第一个量测的是上游（输入层），后两个测的是下游（结构层）。** 它们不能互相替代——见 `§C5.6`。

⚠️ 第二个量有双向歧义：**改判率长期偏高**说明 AI 结构化不可用；**长期接近零**不能直接读作「AI 很准」——也可能是用户根本没在看。两个方向都需要人工抽检，不可单靠该数字下结论。

**检查方式**：见 `§C2.5` 的分层处理规则。违规 = 把「必须确认」类当「默认生效」类处理。

### C2.5 AI 输出的分层处理规则 `[新增]`

**不要把所有 AI 输出都用同一套确认流程。** 一律要求确认会造成高频低风险的确认疲劳；一律默认生效会让 AI 悄悄成为作者。按输出**新增了什么**分层：

| AI 输出 | 新增了什么 | 处理 |
|---|---|---|
| **语义分割**（切分 + 打标签 + 规范化表述） | 涉及用户原意 | **必须确认**。用户确认的是**意义有没有被歪曲**，**不是标签分配**（`§C2.2.2`）。见 `§C5` |
| **新建可被独立引用的对象**（Topic / Claim / Subtopic / Scaffold） | 新断言 | **必须确认**。见 `§C8.2`（嵌套门槛）、`§C12.5`（分裂与确认流程） |
| **对已有内容的标注与关系**（分类、`supports` / `contradicts` / `qualifies`、质询） | 派生标注 | **默认生效 + 可推翻 + 抽样审计 + 计改判率**。见 `§C2.4` |
| **派生视图**（排序、聚合、默认展开、推荐候选） | 无新增断言 | **默认生效 + 可追溯 + 可解释 + 可回退 + 留版本**。**不需确认**。见 `§C7.1` |

**判据一句话**：

```
新增断言  →  必须确认
派生标注  →  默认生效 + 可推翻
派生视图  →  默认生效 + 可解释
```

**关键**：第三、四类的安全**不来自「用户批准过」**，而来自**它们能被推翻、能被解释、且不能反向变成事实**（见 `§C7.1` 单向性约束）。

Artifact    Relation    Evidence    Challenge    Revision

任何具有独立身份、状态、生命周期的对象。类型清单：

contains    derived_from    supports    contradicts    refines    related_to

**硬约束**：Relation 本身是**可追踪对象**（有身份、有来源、可追溯），不是数据库里的一个外键字段。

### C3.5 Revision

见 `§C10`。**禁止覆盖式更新。**

## C4 Debate 结构 `[基线：基线§3]`

**数据形状**（这是结构，不是 UI 布局）：

```
Topic
├── Position / Claim
│   ├── Evidence
│   ├── Mechanism
│   ├── Assumption
│   └── Counterexample
├── Opposing Claim
│   ├── Evidence
│   ├── Mechanism
│   └── Counterargument
└── Vote
```

**关系映射**（实现时必须逐条落地，不可合并）：

| 主体 | 关系 | 客体 |
|---|---|---|
| Evidence | supports / contradicts / qualifies | Claim |
| Claim | assumes | Assumption |
| Claim | explains | Mechanism |
| Claim | challenged_by | Counterargument |

**禁止**：把上述关系简化或归约为一个「证据分数」。

## C5 语义过滤与用户确认（入口） `[基线：基线§4；§C5.1–§C5.6 为新增]`

### 流程 `[基线]`

```
用户输入自然语言
  ↓
AI 分割为若干独立命题 + 打标签
  ↓
向用户展示：切分结果 + 未采用的部分（§C5.2）
  ↓
用户校验意义是否被歪曲（不是批准标签分配，§C2.2.2）
  ↓
写入 Scaffold
```

### 示例 `[基线]`

输入：

> 「现在社会对女性太好了，所以她们根本不懂男性压力。」

AI 分割为三个命题：

```
A. 女性获得了更好的社会待遇
B. 女性不足够理解男性压力
C. A 导致 B
```

⚠️ **全文只有这一个示例，它不足以钉住切分粒度。** 见 `§C5.5.1`。

### 硬约束 `[基线]`

- 语义过滤要回答的是「**这句话包含几个命题**」，**不是**「这句话是真是假」。
- AI 可以**提出**结构。
- **最终确认权属于用户** —— 但确认的是**意义**，不是**标签分配**（`§C2.2.2`）。未经确认不得写入 Scaffold。
- **确认环节不是可选步骤，也不得被优化掉。**
- **哪些文本打什么标签、能否进入结构，由机器决定**，不由用户决定（`§C2.2.1`）。

**关于确认环节的性质（这一条决定产品形态，不要按「减少摩擦」的思路改）**

确认环节是用户**反省自己那句话**的唯一时机。用户在这里第一次看到：*我这句话里其实包含三个命题，其中第三个我没打算说。*

**这是产品价值第一次交付的地方，不是流程摩擦。** 因此：

- 不得设计「一键全部确认」
- 不得默认勾选
- 不得把确认做成无感的后台步骤
- 分割输出应让用户看到**为什么这样切**——尤其是隐含的因果连接词（「所以」「因此」「导致」）被识别为独立命题时，要让这个识别过程可见

### C5.1 AI 侧是过滤器，用户侧是隔离器 `[新增]`

**AI 侧：分割不隔离偏好，它执行偏好。**

```
AI 偏好  →  [ 语义分割 ]  ← 偏差在这里作用  →  只有被贴上标签的片段进入结构
                                                 ↑ 这些恰恰是 AI 筛选后的
```

**保留下来的，正是 AI 偏好的那部分。**

**用户侧：但用户位于 AI 的下游，他能挡住它。**

用户手上有 AI 没有的东西 —— **原文，以及他本来想说什么**。所以两类偏差他都发现得了：

| 偏差形态 | 用户能否发现 | 靠什么 |
|---|---|---|
| **分类错误**（把 A 判成 `supports`） | **能** | 分割结果可见，当场改 |
| **选择性遗漏**（该切出的命题没切出来） | **能** | **用户手上有原文** —— 「我明明说了三句，它只切了两句」 |

**遗漏相对的是用户自己刚说的话，参照物在他脑子里** —— 他对照得出来。

**不要以为「遗漏不可见」**：那只在**用户看不到原始输入**时才成立。

**偏差的实际路径**：

```
AI 偏好  →  分割结果  →  【 用户 】  →  接受 / 换说法 / 不提交
                           ↑ 隔离器在这里
```

**用户不是被动接受者，他是最后一道闸门。** 这正是确认环节存在的意义（`§C5`）。

**但隔离器的每次动作都有代价** —— 见 `§C5.6`。

**⚠️ 按环节分开处理，不要跨环节比较。**

「AI 偏好 / 判断不稳定」这类问题**不是一件事**，它在不同环节有不同形态和不同处理方式：

| 环节 | 它自己要处理的问题 | 处理方式 |
|---|---|---|
| **语义分割** | 偏好影响「什么被贴上标签」→ 选择性遗漏 | `§C5.2` 未采用部分必须可见 |
| **关系判定**（`supports` / `contradicts` / `qualifies`） | 关系判断本身不稳定（与分割无关） | `§C2.4` / `§C2.5` 默认生效 + 可推翻 + 抽样审计 + 计改判率 |
| **检索** | 检索范围由 Scaffold 自己决定，不是外部热度排序 → **流行度偏见不适用** | — |

**关系判定不是语义分割的事。** 分割只管「这是个 Claim」，管不到「这个 Claim 支持那个」。

**不要把「A 环节的手段能否解决 B 环节的问题」当成问题**——它们各自独立，各有各的处理方式。

### C5.2 未进入结构的部分必须可见（硬约束） `[新增]`

确认界面必须**同时**呈现被切出的部分和未被切出的部分：

- 原文**全文渲染**
- 被贴上标签的片段高亮
- **未被切出的部分也必须显式呈现**（灰底 / 折叠但带计数），**不得静默丢弃**
- 判据：用户能一眼看到「这段话里有哪一块系统没处理」

**理由**：**不是**「否则用户看不到遗漏」（用户手上有原文，对照得出来），
而是**降低对照成本**：

- 凭记忆逐句核对，在长文本上会**失效**
- 核对失效 → 用户要么接受错误切分，要么**换说法重来**（`§C5.6`，成本回流到用户）
- 并排展示是让核对变**便宜**，从而让用户能**低成本地**当那道闸门（`§C5.1`）

### C5.3 「标签空值」的用法与边界 `[新增]`

**保留标签空值是对的**，但要清楚它能做什么、不能做什么：

| 遗漏类型 | 空槽位能否捕捉 |
|---|---|
| **类型内缺失**（该有 Mechanism，没有） | **能** —— 槽位空着，用户看得见 |
| **整段遗漏**（这句话没被切出任何命题） | **不能** —— 没有槽位，无迹可寻 |
| **类型外内容**（原文有结构里没有的类型） | **不能** —— 没有对应槽位 |

**建议**：把空槽位做成**持续暴露的完备性提示**（「这个 Claim 的 Mechanism 位置是空的」）。
这比事后审计更强，因为它是**结构性的、自动的**。

但 `§C5.2` 仍然必须做——**空槽位只能表达「已知类型的缺失」，表达不了「未知的缺失」。**

### C5.4 结构层存什么：规范化文本 + 原文快照（已定，非选项） `[新增]`

**三条约束**：

- 原文本**不可修改** → 必须**原样保存**
- 意义**不可修改** → 规范化不得改变语义
- **措辞可以规范化** → 结构层存规范化后的文本

```
原文（不可变）  ──原样保存──→  用于追溯与显示
     │
     └──规范化（意义不变）──→  结构层标签值
```

**两个作用**：

| 作用 | 靠什么 |
|---|---|
| 给用户看的永远是**原话** | `§C5` 的「反省自己那句话」才成立 |
| 进入结构的文本是**标准化的** | 「谁表达得好」这个属性在结构层里**不存在** |

**⚠️ 但这条不能被读作「分割能挡住 AI 偏好」。**
它挡住的只是**风格差异**；**选择性遗漏依然存在**（`§C5.1`），必须靠 `§C5.2` 处理。

### C5.5 分割必须可复现（硬约束） `[新增]`

**不允许「同一输入两次分割结果不同」。** 这是强制要求，不是建议。

**理由**：**用户确认的对象必须是一个稳定的东西。** 若同一输入两次分割不同，
「用户确认」就没有确定的对象 —— 用户确认的是哪一次？

| # | 要求 |
|---|---|
| 1 | **确定性解码**：同一输入 + 同一模型版本 + 同一提示词版本 → 分割结果必须一致（`temperature=0` / 固定 seed） |
| 2 | **确认即冻结**：分割结果一经用户确认，即**冻结为该 Artifact 的组成**，不因后续任何重跑而改变 |
| 3 | **版本升级不追溯**：模型或提示词升级后，**旧的已确认 Artifact 不重新分割**；新版本只作用于新输入 |
| 4 | **重分割 = 新版本**：若原文被编辑而必须重分割，走 `§C10` 版本模型，**产生新版本，不覆盖旧确认** |
| 5 | **记录三个版本**：模型版本 / 提示词版本 / 输入快照。用于解释「为什么当时这样切」 |

**禁止**：把「分割结果不稳定」当作可接受的模型特性。**它是实现错误。**

**检查方式**：同一输入连跑两次，比对结果。不一致 = 违反本约束。

#### C5.5.1 分割质量判据 `[新增·缺口修补]`

⚠️ **原缺口：`§C5.5` 只保证「同样的错切两次」——可复现 ≠ 正确。**
没有质量判据，`§C7.2` 的「未采用片段占比」就没有参照物：占比 5% 到底是切得好，还是原文本来就没什么可切？

**最小可执行判据**（MVP 阶段）：

1. 建一个**人工标注小样本**（条数自定，见 `§C13.1` 第 4 项）。标注内容**只含两项**：该输入包含**几个命题**、每个命题的**边界**。
2. 标注**不由 AI 生成**。由需求方标注或确认——**不能让 AI 同时充当被评估者和评估者**，那等于没有判据。
3. 每次改动分割逻辑，跑这个样本，报**两个数**：`切分数一致率`、`边界一致率`。
4. **现在不设及格线**（`§C7.2`：什么叫「高」等数据）。只要求：样本存在、每次跑、报数。

**为什么不做成自动评分**：分割正确性是「意义是否被歪曲」的判断，属于 `§C2.3` 禁止 AI 做的动作（替用户确认语义）。用 AI 评 AI 会把这条红线绕开。

### C5.6 用户手上的三个动作，以及每个动作的代价 `[新增]`

确认环节**不是**「批准 / 不批准」的二选一。用户实际能做三件事：

| 用户动作 | 它挡住了什么 | 代价 |
|---|---|---|
| **接受** | — | 无 |
| **换说法**（重写输入） | **挡住了 AI 偏好** —— 换到机器能正确切分的表述 | ⚠️ **结构化成本回流到用户** |
| **不提交**（放弃并离开） | 挡住了，但**用户也走了** | ⚠️ **流失**（可见性见 ③） |

⚠️ **确认环节没有「撤回」这个动作。** 用户手上只有这三个。想收回已提交的内容，只有两条路：
换说法重交，或者不提交离开。**已确认写入结构的内容不可删除**（见 `§C10`）。

#### ① 「换说法」与 `§C2.0` 的核心承诺直接冲突

`§C2.0` 承诺：**用户不需要学习任何结构化写法，结构化成本由机器承担。**

但如果用户**必须换说法才能被正确切分**，成本就转移回用户身上了 ——
**这正是本系统声称要消除的东西。**

**判据是频率，不是有无**：

| 换说法的频率 | 含义 |
|---|---|
| **偶尔** | 正常。用户表达确实模糊 —— 这正是 `§C5`「反省自己那句话」的时机 |
| **经常** | **严重问题**。机器切分能力不足，用户被迫迁就 → `§C2.0` 的承诺已失效 |

#### ② 因此必须新增一个指标：换说法率

```
换说法率  =  因「分割不对」而重写输入的用户数 / 提交过的用户数
改判率    =  用户对 AI 结构边的推翻率（§C2.4，下游）
```

**两者是不同的量，测的是不同的事**：

| 指标 | 位置 | 它说明 |
|---|---|---|
| **换说法率** | **输入层（上游）** | 用户是否被迫学习结构化写法 → **直接检验 `§C2.0` 的承诺** |
| **改判率** | **结构层（下游）** | AI 的结构化是否可信 |

**换说法率是更能说明核心问题的那个** —— 它测的是「结构化成本落在谁头上」。
这是本系统对外承诺的核心，也是「为什么现在」的答案。

⚠️ **归因口径**：事件层分不出「因切分不对而重写」和「用户自己改主意」。

**口径：复用 `§C2.2.2` 已经授权的用户动作，不新增任何动作。**

```
用户在确认界面点了「这句话的意义被歪曲了」→ 随后重写   →  计入分子
用户没点，直接重写                                    →  不计入分子（视为自己改主意）
```

`§C2.2.2` 已经给了用户「指出意义被歪曲」这个动作，**它本身就是归因信号**。
记录它即可，**不需要新增原因选择框**——那会违反 `§C7.2`「不新增需要用户配合的动作」。

**代价（必须知情）**：这会把换说法率测成**下界** —— 用户懒得点就漏计。
因此这个数只能看**趋势**，不能当绝对水平读。

#### ③ 「不提交」分两种，只有一种不可观测

⚠️ **这里必须分开，混起来会让一个可观测的观测点被误判为"测不到"。**

| | 定义 | 可见性 |
|---|---|---|
| **A. 已输入后离开** | 用户**已经输入**、AI 已产出分割结果，用户在确认界面**没确认就走了** | ✅ **系统内可见** —— 输入与分割结果都产生了记录 |
| **B. 未输入即离开** | 用户**根本没输入**任何内容就走了 | ❌ **系统内不可见** |
| **`§C5.2` 未采用部分** | **已提交**的输入里有未被切出的片段 | 系统内可见（只要按 `§C5.2` 呈现） |

**A 类必须记录**，它就是 `§C7.2` 观测点清单里的「确认环节：确认耗时 / 中途放弃」。
**它不是新机制，是既有观测点** —— 不要另建一套。

**B 类才是真正的沉默流失**：它不产生任何系统内记录，
只能在系统外观测（用户访谈 / 行为埋点），**不得假装它不存在**。

**两者测的不是同一件事**：A 类是「走到确认这一步又退回去」，B 类是「连门都没进」。
A 类异常高说明确认环节太重或切分太差；B 类异常高说明入口有问题（外部不可见）。

**未确认的输入不涉及撤回**：`§C5.5` 的「确认即冻结」只作用于**已确认**的 Artifact。
用户在确认前重写，就是一次**新输入**，不需要「撤回」这个动作去覆盖旧的。

## C6 证据系统 `[基线：基线§5]`

### C6.1 禁止项

禁止形如 `evidence_score = 8.7` 的标量设计。

理由（用于判断边界情况）：一旦引入标量分，系统即在实质上充当裁判。

### C6.2 必须记录的属性

```
Evidence
├── source / provenance
├── accessibility
├── directness
├── reproducibility
├── methodology
├── sample / selection
├── representativeness
├── temporal validity
├── independence
└── conflict / incentive
```

### C6.3 必须记录的关系

```
Evidence X
├── supports    → Claim A
├── qualifies   → Claim B
└── contradicts → Claim C
```

### C6.4 关键约束

**证据的作用是相对于具体 Claim 定义的，不是证据自带的属性。**

同一个 Evidence 在不同问题上相关性不同：

```
在 Q1 中 → 高度相关
在 Q2 中 → 边缘信息
```

因此：**权重不是 Evidence 的固有属性。**

## C7 权重：上下文属性 `[基线：基线§6；§C7.1 / §C7.2 为新增]`

**设计要点**：把「系统认为这条证据重要」与「这条证据本身重要」分开。

```
Bottom Scaffold        记录事实
  objects / relations     谁是什么
  / provenance            谁支持谁 / 谁反驳谁
                          来源是什么 / 何时发生 / 经历过什么修改
        ↓
Context Scaffold       在此上下文中
  contextual              什么重要 / 什么相关
  interpretation          什么值得展开 / 什么应该被关注
  / relevance
        ↓
Arena Presentation
```

**约束**：Weight 是**关系 / 上下文属性**，不是对象固有属性。

**禁止**：把上下文判断硬编码为对象的固有字段。

### C7.1 上层结构如何产生（不由人设定） `[新增]`

上层（Context Scaffold）的权重**不由人预先设定**，也**不由 AI 直接决定**。

产生方式是：**随样本累积，由底层结果反向影响上层结构。**

**必须写清的三件事**（否则这条机制会与 `§C9` 不变量直接冲突）：

**① 驱动信号是什么。**

| 信号 | 判定 |
|---|---|
| 投票数 / 热度 / 参与量 / 曝光量 | **禁止** —— 违反不变量 #5（Popularity = Evidence） |
| 某类争议反复出现的次数 | 允许 |
| 某个假设被反复质询的次数 | 允许 |
| 某条关系被反复修正的次数 | 允许 |

**允许的信号限于结构性的量，不得含任何表示「受欢迎程度」的量。**

**推荐定义（现在就能定）：跨群共识，而不是总票数。**

上层信号**不是「多少人说」，而是「是否在所有观点群里都成立」**。

| | 「什么重要」 | 「什么跨群成立」 |
|---|---|---|
| 定义 | 总票数 / 热度 / 参与量 | **在每个观点群里都获得认可** |
| 对群大小 | 敏感（大群压倒小群） | **不敏感** |
| 后果 | 退化成流行度 → **违反不变量 #5** | 不退化 |

**采用这条定义的理由**：它的判定条件里就要求**同时**满足所有群，**多数派的规模优势被抵消掉了**。

也就是说：**它在结构上不可能违反 #5，不需要靠人工检查去守。**

**配套要求**：陈述**半随机分发**，不是按热度推送。**从源头掐掉流行度**，而不是事后过滤（见 `§C12.0`）。

⚠️ **但这条定义在 MVP 规模下无法运行。**
「观点群」本身来自分裂（`§C12.5`），而分裂需要用户确认与足够样本。
MVP 阶段（2 个用户、1 个 debate）**不存在观点群**，本机制**全程休眠**。
**实现时按「留白项」处理**（`§T4.1`），不要为它造假的群。

**② 可追溯、可解释。** 上层结构的每一次变化必须留下版本，**不得自动覆盖**（不变量 #9、#10）。用户随时可以问「为什么这条排在这里」，系统必须给出底层依据。

**③ 不需用户确认。**

⚠️ **不要把 `§C12.5` 那套「建议 → 用户确认」搬到上层**（该流程的原始出处为 `基线§11`「分裂机制」）。理由：

- 上层重排是**高频**动作（随样本累积持续变化）
- 每次变化**不新增任何断言**（它只是把已确认的底层事实换个角度排）
- 用户**看不到分群明细**（`§C13.1` 第 1 项：小样本群不展示），逐条确认只会变成盖章
  —— ⚠️ **注意这不是「看不到任何结果」**：用户提交后可看到**聚合结果**，只是看不到它由哪些群构成

**高频 × 低风险 × 无判断依据 = 确认疲劳。**

这与 `§C5` 的分割确认**完全不是一回事**：分割是**低频**、且**涉及用户自己的原话**，值得停下来看。

**例外**：若上层归纳**提议了一个新结构**（例如「这 5 个争议其实属于同一个更高层问题，要不要建个新 Topic」），那就**新增了断言**，必须走 `§C12.5` 的确认流程。

**④ 单向性约束（真正要守的那条）。**

```
底层  →  上层     派生，允许
上层  →  底层     禁止写成事实
```

上层的结果只能影响：**展示顺序 / 默认展开 / 推荐候选**。
上层的结果**不得**写入底层任何字段。

**危险不是「上层没被批准」，危险是上层的相关性判断被固化成底层的真值判断。**

| 允许 | 禁止 |
|---|---|
| 把「被反复质询的假设」排在默认展开位置 | 把「被反复质询」写成「这个假设可疑」 |
| 把「反复出现的争议类型」列为候选新议题 | 把「反复出现」写成「这个问题更重要」 |

**禁止**：把上层权重做成一个不可追溯的自动计算结果。

**一句话**：底层→上层的归纳是**建议的来源**，不是**权威的来源**。它改变的是「什么值得被看见」的候选清单，不是「什么是对的」。**它不需要被批准，但它必须能被解释，而且不许倒流。**

### C7.2 评估层：观测点现在埋，阈值等数据 `[新增]`

**判断**：本文件里所有指标（换说法率、改判率、`unrelated` 占比……）现在都**只是观测点，不是判据**。

**具体阈值现在定不了，定出来也是拍脑袋。**

但有一件事**不能等**：

| | 现在做 | 为什么 |
|---|---|---|
| **观测点（埋点）** | ✅ **必须在 MVP 就埋** | **错过就永久补不回来** —— 前三个月的换说法行为没记录，以后也拿不到 |
| **阈值 / 报警线 / 判据** | ❌ **现在不定** | 没有基线，定出来是拍脑袋；定错了会**误导后续实现** |

**判据一句话**：

```
记录什么    →  现在定
什么叫"高"   →  等数据
```

#### 观测点清单（MVP 就要埋）

| 层 | 观测点 | 它回答 |
|---|---|---|
| **输入层**（`§C5.6`） | 换说法次数 / 用户 / 输入 | 结构化成本是否回流到用户 |
| **输入层**（`§C5.2`） | 未采用片段占比 | 分割覆盖是否足够 |
| **结构层**（`§C2.4`） | 改判率（AI 边被推翻） | AI 结构化是否可信 |
| **结构层**（`§C2.4`） | 用户对自己命题的修改率 | 反省是否发生 |
| **结构层** | `unrelated` 占比 | ontology 覆盖是否足够 |
| **确认环节** | 确认耗时 / 中途放弃 | 确认是否过重 |

**为什么单独监控 `unrelated` 占比**：

给了封闭枚举之后，**落不进枚举的真实情况会被硬塞进最近的类别，或者落进 `unrelated`**。
`unrelated` 因此会变成**垃圾桶类别**。
**它的占比异常升高 = ontology 覆盖不足** —— 不是「数据质量差」。

**系统外观测（系统内测不到）**：

- **未输入即离开**（`§C5.6` ③ 的 B 类）—— 连门都没进，**不产生任何系统内记录**。只能访谈 / 埋点。

⚠️ **注意别把 A 类也归到这里**：`§C5.6` ③ 的 A 类（已输入后离开）**系统内可观测**，
就在本节的「确认环节：确认耗时 / 中途放弃」这个观测点里。**不要为它另建机制。**

#### 观测点如何落到结构上

**观测点是底层事实，评估视图是上层派生。不要新建一套独立监控系统。**

```
底层（Scaffold）    记录事实：谁改了什么 / 谁重写了 / 哪段没被采用
     ↓ 派生（§C7.1）
上层（Context）     聚合视图：比率 / 趋势 / 分布
```

**理由**：符合 `§C7.1` 的单向性约束 —— 底层记事实，上层做派生，**不反向写成事实**。

**禁止**：把评估结果写成底层字段（例如给用户打「表达质量分」）。
那是把**派生视图固化成真值判断**，违反 `§C7.1` ④。

**⚠️ 观测本身会改变行为**（与 `§C12.3` 同一个逻辑）：

若用户知道自己在被计时，确认行为就会变。
**因此观测点应尽量记录既有事件**（重写 / 改判 / 放弃），而**不新增需要用户配合的动作**。
确需新增时，必须同时记录「用户是否知道被观测」。

⚠️ **这条原则与 `§C5.6` ② 的换说法率归因有冲突** —— 见 `§C13.1` 第 3 项。

#### 对 agent 的约束

**不得为上述任何观测点提出具体阈值**（如「换说法率超过 20% 就该……」）。
**没有基线数据的阈值一律是拍脑袋，写进规格会误导实现。**

| 可以做的 | 不可以做的 |
|---|---|
| 定义**怎么记**（事件、字段、口径） | 说「高 / 低」是多少 |
| 定义**怎么算**（分子分母） | 说「超过多少要改设计」 |
| 定义**什么时候看**（每次迭代结束看趋势） | 设报警线 |

## C8 Nested Scaffold `[基线：基线§7 / 基线§8]`

### C8.1 能力

一个 Debate 可以成为另一个 Scaffold 中的 Artifact。

```
Scaffold S0
└── Debate Q0
    ├── Claim A
    ├── Claim B
    └── Evidence X
        └── 发现一个独立分歧
            ↓
Scaffold S1
└── Debate Q1

Q1 derived_from Q0
```

关系可以更复杂：

```
Q0 ├── related_to   → Q2
   ├── refines      → Q3
   └── derived_from → Q4
```

**核心**：结构本身也可以成为内容。

### C8.2 嵌套门槛（硬约束）

**默认行为是 `flat + relation`，不是嵌套。**

只有当以下**四条全部满足**时才考虑 `nest`：

1. 具有独立生命周期
2. 具有独立上下文
3. 脱离父节点后仍具有独立意义
4. 需要独立讨论 / 修正 / 验证

不满足时，只能使用：

```
related_to
derived_from
```

**明确禁止**：以「Scaffold 可以解释 Scaffold」为由，再构造一层 Scaffold 去解释它。

**理由（用于判断边界）**：无限递归会重新引入权威层。能力越通用，越需要限制其适用边界。

## C10 版本模型 `[基线：基线§15]`

**核心原则**（基线§15，勿丢）：

> **记录，不停止，不限制。**

这是版本模型的**总原则**，下面的具体规则都是它的推论。

**推论**：**不得为了「避免冲突」而阻止用户操作。**
冲突靠**记录与版本**处理，**不靠禁止**。

**禁止**默认覆盖：

```
Q → update → Q          ← 不允许
```

**必须**保留分支：

```
Q(v1)
├── user A → Q(v2a)
└── user B → Q(v2b)
```

后续操作 `merge / compare / reject / derive` **全部留痕**。

**目标形态**：`Current State + Revision History`，不是 CRUD。

⚠️ **撤回已提交内容：已定 —— 不提供该功能。**
本原则与「用户撤回自己提交的内容」的关系**不需要再讨论**：用户**不能删除已发送的话**。
确认环节想收回，只有 `§C5.6` 的三条路（接受 / 换说法重交 / 不提交离开）；
已确认写入结构的内容**只进不退**，靠 `revision` 记录后续变化，不靠删除。

## C11 并发（本阶段首要目标） `[基线：基线§14]`

### C11.1 需要覆盖的场景

| 场景 | 描述 |
|---|---|
| 并发提交 | A confirm Claim / B confirm Claim |
| 并发修改 | A: v1 → v2a / B: v1 → v2b |
| 并发创建子议题 | A 创建「男性压力」/ B 创建「男性压力问题」 |
| 投票竞争 | Vote 与 Topic close 同时发生 |
| AI / Human race | AI 正在整理 v1，用户把 v1 改成 v2，AI 结果返回 |

### C11.2 需要被真实问题逼出来的机制

```
versioning
optimistic locking
idempotency
conflict handling
event / history
stale client handling
transaction boundary
cache consistency
realtime update
```

**方法**：先让真实并发把问题打出来，再决定引入哪些机制。

#### 「真实并发」的判据 `[新增·缺口修补]`

⚠️ **原缺口**：本节说「真实并发」，任务卡第 10 步说「制造两个用户同时操作」，两者未对齐。
不对齐的后果是：agent 脚本化造两个客户端，就宣布拿到了「真实并发问题」。

| 动作 | 判定 |
|---|---|
| 准备**独立操作主体**（两个客户端 / 两个会话 / 两个进程） | ✅ **允许** —— 这是「制造条件」 |
| 让它们在**无协调**的情况下操作同一份状态 | ✅ **允许**，且**必须** |
| 直接改数据库 / 手工补状态 | ❌ **禁止** —— 那是剧本，不是并发 |
| 注入延迟 / 写死竞争窗口来「制造」冲突 | ❌ **禁止** —— 同上 |
| 一轮跑完没暴露问题 | ✅ **如实汇报「本轮未暴露」** —— 不得伪造 |

### C11.3 明确禁止

**在本阶段真实并发问题出现之前**，禁止预先引入：

- Kafka / 消息队列
- Redis Cluster
- 分布式锁

**理由**：这些是待被问题证明的必要性，不是设计前提。

## C12 投票 `[基线：基线§9 / 基线§10 / 基线§11 / 基线§12 / 基线§13]`

### C12.0 匿名与随机化 `[基线：基线§13]`

（基线§13，勿丢）

| 项 | 要求 |
|---|---|
| **匿名** | 初始设计即匿名 |
| **随机抽样 / 随机展示议题** | **不是**按热度，**不是**按时间 |
| **降低身份 / 粉丝 / 声望影响** | **尽可能降低** —— 这是**设计目标**，不是附带效果 |

**理由**：这三条是**同一个目标**的三个方面 —— 让投票反映**判断**，而不是反映投票者的**影响力**。

**与 `§C7.1` 的关系**：`§C7.1` 的「半随机分发」**正是这条的同一个机制**（从源头掐掉流行度）。
**两者是同一件事，不要当成两条独立要求去做。**

### C12.1 语义边界 `[基线：基线§12]`

投票记录的是**公共偏好 / 公共判断**。**不是真理判定。**

### C12.2 UI 必须分离的四个量 `[基线：基线§12]`

```
Public Preference      公众倾向：A 61% / B 39%
Argument Support       论点支持：A 4/6 claims 有支持材料
Evidence Status        证据状态：3 verified / 3 unresolved
Main Dispute           主要争议：Premise P1
```

**禁止**呈现为：

```
A 61% → A 更正确
```

### C12.3 匿名投票需记录的字段 `[基线：基线§13]`

```
sampling
question_version
argument_version
timestamp
prior_results_visible
repeat_participation
```

**关键**：投票结果本身会影响后续投票（先看到 A 80% 再投票，该结果已成为实验变量）。

因此：**Vote Result 与 Observation Condition 必须一起记录。**

### C12.4 结构继承 ≠ 判断继承 `[基线：基线§10]`

允许：

```
A1 derived_from A
```

禁止：

```
A1 inherits votes from A
```

### C12.5 多观点与分裂 `[基线：基线§9 / 基线§11]`

- 数据结构**禁止写死二元**。允许 `A / B`，也必须能承载 `A1 / A2 / A3` 与 `A / B / C / D`。
- **禁止自动分裂旧票**：

```
原始：      A = 61%   B = 39%
A 分裂为：  A → A1 + A2
禁止推导：  A1 = 30%  A2 = 31%
```

旧票属于**旧问题版本**。新结构必须产生**新的投票上下文**。

- 分裂只能由 Evidence / 用户行为 / 论证结构**提示**，流程为：

```
Evidence
  ↓ 提示可能存在一个独立问题
用户确认
  ↓
创建新 Topic / Scaffold
```

**禁止**：

```
Evidence → 系统自动生成子节点
```

- 任何结构关系必须满足四项：**可确认 / 可拒绝 / 可修改 / 可追踪**。
