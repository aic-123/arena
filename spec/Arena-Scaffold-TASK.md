## T0 铁律（先读这一节）

### T0.1 三条硬约束 —— 违反即实现错误

1. **`§C9` 的 11 条不变量**
2. **`§C5.5` 分割必须可复现** —— 同一输入 + 同一模型版本 + 同一提示词版本 → 结果必须一致
3. **`§C2.2` 分割环节必须是纯粹分割** —— 不带建议、倾向、解读、评价

### T0.2 编码纪律

- **最小改动**。不做顺手重构、重命名、格式化；diff 中不夹带无关变更
- 与周围代码保持一致（命名 / 结构 / 错误处理 / 测试风格）
- **不凭经验假设技术栈**，从仓库实际内容验证
- 修 bug 前**先复现**：先写失败测试，或给出可复现步骤
- 用户表达**原样保存**（`§C2.2.1`）。措辞可规范化，**意义不可变**
- 附录里被标记为「理由」「为什么」的段落是**判据**，不是功能清单，**不要当需求去实现**

### T0.3 不许自决

- 不得为 `§C7.2` 的任何观测点提**具体阈值**（如「换说法率超过 20% 就该……」）。没有基线数据的阈值一律是拍脑袋
- 不得把**评估结果写成底层字段**（例如给用户打「表达质量分」）
- 不得在真实并发问题出现之前引入 Kafka / 消息队列 / Redis Cluster / 分布式锁

## T1 目标

**一句话**：Arena 是建立在 Scaffold 之上的多人结构化讨论系统。

**层职责不可交叉**：Arena 承载讨论行为；Scaffold 承载对象与关系；Nested Scaffold 承载结构间组合（默认不启用，`§C8.2`）。依赖方向 Arena `uses` Scaffold，**不可反向**。

**AI 的定位**：Secretary / Organizer / Detector。**不是 Judge。**

**本阶段唯一目标**：`§T3` 那一条链。范围超出该链的功能，一律不做。

**非目标**：不是完整版 Reddit；不是完整版「AI 辩论平台」；不是通用知识框架。

## T2 工作顺序

按序执行，不要一次性构建完整系统。

**前置**：第 01 步之前先交付《选型声明》（`§T4.2`）。

```
01  读样本
02  找最小 Artifact
03  建最小 Scaffold
04  跑通一个 Debate
05  加语义确认
06  埋观测点
07  加 Claim / Evidence / Challenge
08  加 Revision
09  加 Vote
10  制造两个用户同时操作
11  记录第一个真实并发问题
12  再引入成熟方案
13  修掉它
14  再跑一遍
```

**三个重点步骤**：

| 步 | 要求 |
|---|---|
| **06** | 观测点必须**随 MVP 一起埋**（`§C7.2`）。阈值可后定，**埋点错过就永久补不回来** |
| **10** | 准备**独立**操作主体（两个客户端 / 会话 / 进程），让它们**在无协调下**并发操作同一份状态。**禁止**人为干预状态（改库 / 注入延迟 / 写死竞争窗口）—— 那是剧本，不是并发 |
| **11** | 交付形式：**现象 / 复现步骤 / 根因**，三者缺一不算完成。若本轮**未暴露**问题，如实汇报「本轮未暴露」，**不得伪造** —— 这本身是有效结果 |

**第 10 / 11 步是本阶段的核心交付，不是可选项。**

## T3 完成判据

MVP 只证明一条链跑通：

```
用户提问 → AI 语义分割 → 用户确认 → 形成 Topic / Claim
        → 多方提交观点 → Evidence / Mechanism / Assumption
        → Challenge → 发现分歧 → 产生可能独立的 Subtopic
        → 用户确认 → 新 Scaffold / Debate → 独立讨论 → Vote
        → 上下层关系可追踪
```

**判据**：这条链跑通，即证明 Nested Scaffold 是系统能力，而非架构设想。

**「跑通」的可验证形式**：给出**一条可复现的命令或一组可复现步骤**，从空状态跑到链尾，
中途不手工改库、不手工补数据。形态自选（CLI / 脚本 / 本地页面均可），按 `§T4.2` 声明。

**必须同时交付**：

1. 第 11 步记录到的**第一个真实并发问题**（现象、复现步骤、根因）
2. **`§C7.2` 的观测点全部埋设完成** —— 随 MVP 一起交付，不是「以后补」

## T4 留白项：自选 + 声明（不再停下提问）

### T4.1 A / B 两类，不得用同一套放行

| 类 | 范围 | 处理 |
|---|---|---|
| **A · 实现细节，原则中立** | `§C13.A`：schema / 框架 / WebSocket / API / UI… | 自选 + 声明 |
| **B · 算法与判据，可能触碰不变量** | `§C13.B`：投票算法 / 自动分裂阈值 / 自动合并算法 / 归纳算法 / 锁策略… | 自选 + 声明 + **自证不违反哪几条不变量** |

**B 类自证写不出来 → 停下提问。** 这一类不能用声明制放行。
（A 类选错只是不好用；B 类选错等于绕过不变量。）

### T4.2 《选型声明》必须在写第一行代码之前交付

单独一页，含四项：

```
1. 选了哪个
2. 为什么不选另一个
3. 引入了什么依赖
4. （B 类）为什么不违反不变量
```

**每条声明必须可核验**：对应一个可检查的事实（依赖清单 / 文件路径 / 配置项），不是叙述。

**B 类第 4 项不能只是说法，必须落成一条可执行的否证检查**：

```
声明：选了 X，它不违反 #4（Vote = Truth）
检查：<一条命令 / 一个断言> 证明产物里不存在 <该不变量禁止的东西>
例：  grep -rn 'total_score\|verdict\|truth_value' <输出结构定义>   →   无命中
```

**检查跑不通 = 声明不成立 = 停下提问。**

### T4.3 默认建议（可推翻，按 `§T4.2` 的格式声明即可）

MVP 走**单机、单进程、本地文件或 SQLite、零外部服务**。

理由：第 10 步需要能起两个独立客户端，单进程最容易做到；同时避开 `§C11.3` 禁止的组件。

## T5 什么时候必须停下来提问

- 改动开始**扩散到多个模块**
- 需要修改 `§C9` 不变量中的**任何一条**
- 需要引入**新依赖**（先说明现有依赖为何不满足）—— **这是留白项唯一保留的阻断**
- 出现 `§C9` 第 11 条的**分层污染**
- **`§T4.1` 的 B 类自证写不出来**
- 需求不明确，且**猜测的代价高于提问**

---

## T6 汇报格式

每次改动后说明五项：

```
1. 改了什么
2. 为什么这样改
3. 哪里还不确定
4. 哪些风险需要你知情
5. 验证方式与结果（可复现的命令）
```

**若本次动到了留白项**，另附《选型声明》（`§T4.2`）。
