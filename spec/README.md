# `spec/` —— 这个系统是照着什么建的

代码里到处是 `§C9 #5`、`§T4.2`、`基线§18` 这样的引用。**那些号指向的就是这个目录里的文件。**

## 四份文件，四种用途

| 文件 | 是什么 | 什么时候读 |
|---|---|---|
| `Arena-Scaffold-AGENT.md` | **身份与姿态** —— 干活的那个 agent 该以什么立场做事 | 先读这个 |
| `Arena-Scaffold-TASK.md` | **任务卡** —— 要干什么、什么算干成、什么时候必须停下来问 | 通读 |
| `Arena-Scaffold-CONSTRAINTS.md` | **约束附录** —— 全部设计约束**及其理由** | **按需查，不要通读** |
| `Arena-设计基线-原始稿.md` | **最早的设计稿** —— 上面三份的母本 | 溯源时查 |

## 命名空间：`§` 号必须带前缀，省略即歧义

| 前缀 | 指向 | 在代码里出现次数 |
|---|---|---|
| `§Cn` | `Arena-Scaffold-CONSTRAINTS.md` | 659 |
| `§Tn` | `Arena-Scaffold-TASK.md` | 89 |
| `基线§n` | `Arena-设计基线-原始稿.md` | 0（只在 `CONSTRAINTS` 的溯源标记里用） |

所以 `DECLARATION.md` 里那句 `§C9 #5 #7` 的意思是：去 `Arena-Scaffold-CONSTRAINTS.md`
找第 9 节、看第 5 和第 7 条不变量。**可以逐条对上。**

## 规则冲突时的优先级

```
用户当场明确指示  >  TASK.md  >  CONSTRAINTS.md  >  现有代码规范  >  agent 自身默认行为
```

## 一条读法上的提醒

`CONSTRAINTS.md` 里凡是标着「理由」「为什么」的段落，**是判据，不是功能清单**。
它们的用途是**判断边界情况**，不是「待实现的需求列表」。
把理由当需求去实现，会造出一堆没人要的功能。

同理，`TASK.md` 的 `§T4` 是一张**留白项**表（文档没规定、由实现者自选并声明的地方）——
它登记的是**决策点**，不是遗漏。

## 和代码怎么对上

`CONSTRAINTS.md` 的 `§C9` 是 11 条不变量。其中每一条在代码里都有一条**可执行的否证检查**
（`checks.py` 的 `B1`–`B13`），跑法：

```bash
python checks.py        # 退出码 0 = 13 条全过
```

**这些检查不是「测试通过」，是「声明成立」。** 它们跑的是 `grep` 产物里
*不许出现的东西* —— 命中即《选型声明》不成立。

`DECLARATION.md` 记的是**每个选择连同它的否证检查** —— 它回答的是
「我为什么这么选」，不是「这个功能现在能不能用」。

**这两件事在这个仓库里被刻意分开**，因为混起来最容易骗人：
一个选择可以**写进声明、跑通检查**，同时**产品表面根本没有入口**。
读的时候请分清楚「声明里写了」和「你能用上」。
